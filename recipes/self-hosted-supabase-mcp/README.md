# Self-Hosted Supabase for Open Brain (Lean, with MCP)

> Run Open Brain entirely on your own machine: a lean self-hosted Supabase stack with Docker Compose, the six Open Brain MCP tools, and file storage, with no cloud account and no Kubernetes.

## What It Does

This recipe starts a trimmed-down copy of Supabase's official self-hosting stack and runs the [self-hosted LLM MCP server](../../integrations/self-hosted-llm-mcp/) on it. Your AI client gets the same six tools as the core Open Brain server (`capture_thought`, `search_thoughts`, `list_thoughts`, `thought_stats`, `search`, `fetch`). Thoughts are stored in a Postgres database on your machine, and embeddings and metadata come from a model server you run yourself.

It runs 5 of the official stack's 11 services, all the time:

| Service | Why it runs |
|---------|-------------|
| `db` | Postgres with pgvector, holding the `thoughts` table at 1536 dimensions |
| `rest` | The REST API the MCP server uses to read and write thoughts |
| `api-gw` | The gateway on port 8000 that every request goes through |
| `functions` | The Edge Functions runtime that serves the MCP server |
| `storage` | File storage, with one private bucket, `ob1-files`, ready for files such as product manuals or photos of where things are stored |

A one-shot helper, `ob1-init`, creates the `ob1-files` bucket the first time the stack starts and then exits.

**What the lean stack leaves out, and what that costs:**

- **No web dashboard by default.** Supabase Studio is an optional add-on (see [Optional: the web dashboard](#optional-the-web-dashboard)). Where other Open Brain guides say "paste this into the SQL Editor", use the `psql` route in [Run SQL without the dashboard](#run-sql-without-the-dashboard) instead.
- **No user logins.** Supabase Auth doesn't run. The MCP server checks its own access key, so Open Brain doesn't need it, but [`dashboards/open-brain-dashboard`](../../dashboards/open-brain-dashboard/) does not work on this stack, because it signs users in through Supabase Auth.
- **No realtime feeds and no connection pooler.** No Open Brain contribution uses them.
- **No image resizing by default.** Storage keeps and returns files as they are. The `images` profile starts the resizing service for later features, but turns nothing on by itself.

**How it differs from the other self-hosted options:**

- [`recipes/local-brain-no-mcp`](../local-brain-no-mcp/) is for networks that block MCP: it runs the full Supabase stack and exposes plain HTTP endpoints instead of MCP, with 768-dimension embeddings by default. This recipe is canonical MCP at 1536 dimensions, on a much smaller stack.
- [`integrations/kubernetes-deployment`](../../integrations/kubernetes-deployment/) runs the same six tools on Kubernetes with plain Postgres. This recipe needs only Docker Compose on one machine.

This recipe reuses Supabase's official stack rather than copying it: `setup.sh` clones the official files at one pinned release (`self-hosted/v0.8.5`) into an ignored `supabase/` folder, and `lean.override.yml` only changes which services start and how.

## Prerequisites

- A Mac or Linux machine with **Docker and Docker Compose** (tested with Docker Desktop 4.96 and Compose v5.6.1 on macOS). Windows is not tested.
- **`git`** and **`openssl`** (both come with macOS and most Linux distributions).
- A full checkout of this repository: the stack runs the MCP server straight from [`integrations/self-hosted-llm-mcp/`](../../integrations/self-hosted-llm-mcp/).
- **An OpenAI-compatible model server** with one embedding model and one chat model, meeting the [self-hosted LLM MCP server's model requirements](../../integrations/self-hosted-llm-mcp/#choosing-an-embedding-model): the embedding model must return 1536 numbers. The tested pair is Ollama on the host with `qwen3-embedding:4b` and `llama3.1:8b`.

## Credential Tracker

Everything secret is generated for you and kept in `supabase/docker/.env`, which git ignores. You never paste a secret into a tracked file.

```text
SELF-HOSTED SUPABASE FOR OPEN BRAIN -- CREDENTIAL TRACKER
---------------------------------------------------------

GENERATED BY setup.sh (read them from supabase/docker/.env)
  MCP access key:          MCP_ACCESS_KEY      (your AI clients use this)
  Dashboard login:         DASHBOARD_USERNAME / DASHBOARD_PASSWORD   (optional web dashboard)
  Service role key:        SERVICE_ROLE_KEY    (storage check; never give it to a client)

YOU FILL IN (model server, spec 004 names)
  Embedding API base:      ____________   (for example http://host.docker.internal:11434/v1)
  Embedding model:         ____________
  Chat model:              ____________
```

## Steps

1. **Run the setup** from this folder:

   ```bash
   cd recipes/self-hosted-supabase-mcp
   sh setup.sh
   ```

   It clones Supabase's stack at the pinned release into `supabase/`, checks that your Docker Compose can read this recipe, generates every secret into `supabase/docker/.env` (including `MCP_ACCESS_KEY`), and adds blank model settings. It prints one line per step, for example `clone: completed` and `secrets: completed`. It never prints a secret.

   Running it again is safe. It completes whatever is missing, for example after an interrupted run, and reports the rest as `already present`. It never regenerates a Supabase key in an existing `.env`, because that would lock you out of the data and logins those keys protect.

2. **Point it at your model server.** Open `supabase/docker/.env` and fill in the model settings at the end:

   ```text
   EMBEDDING_API_BASE=http://host.docker.internal:11434/v1
   EMBEDDING_MODEL=qwen3-embedding:4b
   CHAT_MODEL=llama3.1:8b
   ```

   The containers reach a server on your own machine as `host.docker.internal`, on both macOS and Linux; `localhost` would mean the container itself. Leave `CHAT_API_BASE` blank to use the embedding server for chat too. The [MCP server's README](../../integrations/self-hosted-llm-mcp/#configure) explains every setting.

3. **Start the stack**:

   ```bash
   docker compose up -d
   docker compose ps
   ```

   After a minute, `docker compose ps` shows `db`, `rest`, `api-gw`, `functions` and `storage` as healthy, and `ob1-init` as exited. On the first start, Postgres creates the Open Brain schema from [`db/ob1-schema.sql`](db/ob1-schema.sql), which is `docs/01-getting-started.md`'s SQL at 1536 dimensions.

4. **Run the setup check.** Read your key first:

   ```bash
   KEY=$(grep '^MCP_ACCESS_KEY=' supabase/docker/.env | cut -d= -f2-)
   curl -s -H "x-brain-key: $KEY" http://localhost:8000/functions/v1/self-hosted-llm-mcp/setup-check
   ```

   Every check should pass. If one fails, its message says which setting to fix; see [Troubleshooting](#troubleshooting).

5. **Connect your AI client.** For Claude Code:

   ```bash
   claude mcp add --transport http open-brain-local "http://localhost:8000/functions/v1/self-hosted-llm-mcp?key=$KEY"
   ```

   Clients on other machines in your local network use your machine's address instead of `localhost`. Cloud-hosted clients, such as claude.ai custom connectors, cannot reach this stack: it is only on your machine and local network.

6. **Try it.** Ask your client to capture a thought, then search for it with different words. Review which tools your clients load with the [MCP Tool Audit & Optimization Guide](../../docs/05-tool-audit.md).

7. **Optional: check file storage** (see [File storage](#file-storage)).

### File storage

The stack keeps files in Supabase Storage, in the private bucket `ob1-files`. Open Brain's MCP tools don't attach files yet; this check shows the storage works:

```bash
SRK=$(grep '^SERVICE_ROLE_KEY=' supabase/docker/.env | cut -d= -f2-)
printf 'storage check\n' > check.txt
curl -s -H "apikey: $SRK" -H "Authorization: Bearer $SRK" -H "Content-Type: text/plain" \
  --data-binary @check.txt http://localhost:8000/storage/v1/object/ob1-files/check.txt
curl -s -H "apikey: $SRK" -H "Authorization: Bearer $SRK" \
  -o check.out http://localhost:8000/storage/v1/object/ob1-files/check.txt
cmp check.txt check.out && echo "storage works"
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8000/storage/v1/object/ob1-files/check.txt
```

The last request has no credentials and is refused (Storage answers `400`). The service role key can do anything in your stack: use it only from your own machine.

Files live in a Docker volume named after this project, ending in `ob1-storage`, not in a folder you can browse. Docker Desktop's shared folders on macOS don't support the extended file attributes Storage needs, and a Docker volume does.

### Optional: the web dashboard

Start Supabase Studio when you want to browse thoughts, look at stored files, or run SQL in a browser:

```bash
docker compose --profile ui up -d
```

Open `http://localhost:8000` and sign in with `DASHBOARD_USERNAME` and `DASHBOARD_PASSWORD` from `supabase/docker/.env`. The `thoughts` table is under Table Editor, and the `ob1-files` bucket is under Storage. The Authentication pages do not work, because the lean stack has no Supabase Auth.

Stop it again without touching the rest:

```bash
docker compose --profile ui stop studio meta
```

### Run SQL without the dashboard

Postgres has no port on your machine in the lean stack. Run SQL inside the database container instead:

```bash
docker compose exec db psql -U postgres
```

To run a file that another Open Brain guide tells you to paste into the SQL Editor:

```bash
docker compose exec -T db psql -U postgres < path/to/file.sql
```

The Open Brain tables are owned by `postgres`, as on Supabase Cloud, so later extensions' SQL works the same way.

### Add more Open Brain MCP servers

The stack can serve other Open Brain Edge Functions next to this one, for example the [professional CRM](../../extensions/professional-crm/) or [household knowledge](../../extensions/household-knowledge/) servers. Mount each function folder into the `functions` service in your own Compose override, the way `lean.override.yml` mounts `self-hosted-llm-mcp`, run its SQL with the `psql` route above, and recreate the runtime with `docker compose up -d --force-recreate functions`.

**Security warning:** on a self-hosted stack, JWT checking for Edge Functions is one setting for all of them (`FUNCTIONS_VERIFY_JWT`, off by default). Every function on this stack is reachable without a Supabase JWT, and every function sees the service role key. So each function must check its own credentials, as the MCP server does with its access key. Do not expose port 8000 beyond the networks you trust.

### Stop, restart, and remove

| Task | Command |
|------|---------|
| Stop everything (data kept) | `docker compose down` |
| Start again | `docker compose up -d` |
| Apply changed settings in `.env` | `docker compose up -d --force-recreate functions` (a plain restart keeps the old settings) |
| Save the database to a file | `docker compose exec -T db pg_dump -U postgres postgres > backup.sql` |
| Remove the stack **and delete all stored files** | `docker compose down -v` |
| Start over completely | `docker compose down -v`, then delete the `supabase/` folder (this deletes the database too) |

Where your data lives:

- **Database:** `supabase/docker/volumes/db/data` in this folder.
- **Files:** the Docker volume ending in `ob1-storage`.
- **Secrets:** `supabase/docker/.env`.

The containers restart on their own after a reboot once Docker is running. The `pg_dump` line above saves the database only; it does not copy stored files.

### Changing the Supabase version

`setup.sh` is pinned to Supabase's self-hosted release `self-hosted/v0.8.5`, the only version this recipe was tested with. If `supabase/` holds another version, `setup.sh` stops and names both. To try another release, change `PIN` at the top of `setup.sh`, delete the `supabase/` folder, and run `sh setup.sh` again. That creates new secrets and a new, empty database.

### Starting over

`setup.sh` stops if a Supabase key in an existing `supabase/docker/.env` is missing or still has its example value, because regenerating it would invalidate data and logins made with the old key. To start from scratch, follow "Start over completely" in the table above, then run `sh setup.sh` again.

## Expected Outcome

- `docker compose ps` shows `db`, `rest`, `api-gw`, `functions` and `storage` healthy, `ob1-init` exited, and no other services.
- The setup check from step 4 passes every check.
- Your AI client lists six Open Brain tools. A captured thought is stored with a 1536-number embedding, and a search in different words finds it.
- The storage check prints `storage works`, and the request without credentials is refused.
- After `docker compose down` and `docker compose up -d`, or a reboot, your thoughts and files are still there.

## Troubleshooting

**`setup.sh: docker not found on PATH`** (or `git`, or `openssl`): install the named tool and run `sh setup.sh` again.

**`Docker Compose … cannot read this recipe's compose files`**: this recipe uses Compose's `include` with override tags. Update Docker Desktop or the Compose plugin; the message names the version you have and the version tested.

**`supabase/ is at …, but this recipe is pinned to …`**: see [Changing the Supabase version](#changing-the-supabase-version).

**`supabase/docker/.env has no …` or `… still has its .env.example value`**: see [Starting over](#starting-over).

**The setup check says the model server is unreachable**: use `host.docker.internal`, not `localhost`, for a server on your own machine, and make sure the server listens on all interfaces or on Docker's bridge. Ollama on macOS works as installed.

**Port 8000 is already in use**: set `API_GW_HTTP_PORT` in `supabase/docker/.env` to a free port, run `docker compose up -d`, and use that port in every URL above.

**A changed setting has no effect**: recreate the runtime with `docker compose up -d --force-recreate functions`. A plain `docker compose restart` keeps the old environment.

**Uploading a file fails with a 500 error**: Storage must use the `ob1-storage` Docker volume, which `lean.override.yml` sets. A bind-mounted host folder fails on macOS because it lacks extended attributes.
